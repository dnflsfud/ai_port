# 구조 감사 1~4번 수정 내역

**완료: 2026-09-15.** 운영·비교 포트폴리오 전체 재계산, 두 운영 번들 생성, 레지스트리 검증까지 통과했다. 현재 운영 판정은 `PRODUCTION`이며 8개 검사가 모두 True다.

사용자 요청에 따라 네 항목을 구현했다. 계산 파라미터와 variant 플래그는 변경하지 않았으며, `business_day_calendar_enabled=True`의 데이터 정확성 경로를 바로잡았다. 기존 설정에서 이 플래그가 꺼진 역사적 경로는 유지한다.

## 1. 반복 실행으로 사라지던 목표주가 기저 경고

`src/tg_basis_guard.py`에 상태 저장을 분리했다. 각 실행 폴더의 `tg_basis_state.json`이 정상 기준값과 미해결 종목을 보관한다. 정상 종목만 기준을 갱신하고 미해결 종목은 원래 기준으로 계속 검사한다. 상태 파일은 임시 파일에 완전히 기록한 후 원자적으로 교체한다.

기존 metrics의 jump에는 `previous`가 있으므로 첫 실행 때 그 원래 기준을 복구한다. metrics에도 상태 사본을 남겨 sidecar 누락 시 이미 감지한 이상을 잊지 않는다. 손상된 상태는 정상 상태로 초기화하지 않고 오류를 낸다. 관측값 누락도 기존 경고를 해제하지 않는다.

정상 기저 복구는 자동 처리된다. 실제 벤더 기저 변경을 확인한 경우에는 아래 명령으로 확인 사유를 기록할 수 있다. 이 명령은 실제로 실행하지 않았다.

```text
python scripts/acknowledge_tg_basis.py --run-dir outputs/codex_causal_rank_65 --ticker AAA --expected-ratio 1.5 --reason "확인한 벤더 변경 사유"
```

현재 미해결 값과 지정 값이 일치해야 하며, 절대 비율 범위를 여전히 위반하면 해제할 수 없다. `tg_basis_acknowledgements.json`에 이력이 남는다. 기존 metrics·번들은 수정하지 않으며 다음 정상 실행에서 모든 운영 조건을 다시 검사한다.

## 2. 휴장일 실적발표 누락

`src/trading_calendar.py::align_earnings_events()`가 원본 발표일을 최초의 동일/이후 거래일에 매핑한다. `Earnings_Timeline`과 대체 시트 `Earnings_Date` 모두 지원하며, 미래 이벤트를 마지막 관측일로 당기지 않는다. 같은 거래일로 모이는 발표는 0/1 플래그로 통합하고, 원본 이벤트 수·이동 수·범위 밖 이벤트 수를 따로 기록한다.

로더에 원본 발표일도 보존한다. 매핑된 행렬을 PEAD 등 기존 소비처에 전달하므로 소비처에서 다시 날짜를 정렬해도 이벤트가 소실되지 않는다. 정상 거래일의 이벤트와 전체 신호의 기존 1일 집행 지연은 유지한다.

## 3. 리밸런싱 안내 달력

로더와 exporter가 같은 `BusinessDays` 해석 함수를 사용한다. 제공된 거래일 범위 안에서는 원본 날짜를 사용하고, 미래 구간은 XNYS 세션으로 확장한다. 미래 달력 의존성이 없으면 평일 추정으로 대체하지 않고 설치 필요 오류를 낸다.

`requirements-full.txt`에 `exchange-calendars>=4.11,<5`를 추가했으며 현재 환경에는 4.13.2를 설치했다. API 근거는 [exchange_calendars 공식 문서](https://github.com/gerrymanoim/exchange_calendars#working-with-sessions)다.

운영 메타데이터에는 `XNYS`를 명시한다. 번들 검증도 다음 날짜를 해당 달력으로 다시 계산한다. §S18.8에서 결정된 두 포트폴리오의 공통 일정 일치 검사는 유지한다.

## 4. 캐시와 현재 데이터의 혼합 방지

`src/run_integrity.py`가 입력 워크북/FX 파일의 SHA-256·크기·나노초 수정시각과 계산 코드 지문을 캡처한다. 파일 해시 계산 도중 변경, 로딩 도중 변경, 실행 완료 전 변경을 검사한다.

결과 pkl, metrics, manifest에 동일한 `run_contract`를 저장한다. 계약에는 최종 적용 설정의 해시·전체 입력 날짜·종목 순서도 포함한다. 데이터 빈티지는 실행 종료 시점이 아니라 실제 입력을 캡처한 시점을 기록한다.

export는 같은 방식으로 현재 계약을 만들고 pkl과 비교한다. 마지막 날짜가 같아도 중간 거래일, 펀더멘털, 설정, 코드가 달라지면 재사용을 거부한다. 구형 pkl에는 계약이 없으므로 첫 재생성이 필요하다. 새 실행에서는 출력 디렉터리만 바뀐 경우는 같은 계산으로 인정한다.
